# OCS One — Manufacturing ERP

Operations control system for OCS Oorja Green Pvt. Ltd. — end-to-end manufacturing execution for LiFePO4 battery packs, covering cell receiving, grading, matching, manufacturing stages, quality control, and logistics dispatch.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 8080, proxied to `/api`)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run lint` — ESLint with zero-warning enforcement
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string, `SESSION_SECRET` — JWT signing secret

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5 + Pino logging
- DB: PostgreSQL + Drizzle ORM
- Auth: JWT in httpOnly cookie (`ocs_token`), bcryptjs password hashing
- Security: Helmet, CORS (ALLOWED_ORIGINS env), express-rate-limit (300/min global, 20/15min auth)
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval split mode (from OpenAPI spec → `lib/api-client-react`, `lib/api-zod`)
- Build: esbuild (CJS bundle)
- Frontend: React 19 + Vite, Wouter v3, React Query, shadcn/ui, Tailwind

## Architecture decisions

- **JWT in httpOnly cookie** — eliminates XSS token theft; cookie named `ocs_token`, signed with `SESSION_SECRET`. Every non-public route is behind `requireAuth`. Public routes are only `/api/healthz` and `/api/auth/*`.
- **Postgres sequences for ID generation** — `mfg_order_seq`, `mfg_battery_seq`, and `ecf_correction_seq` created on startup via `seed.ts`; helpers use `SELECT nextval(...)` inside transactions to avoid race conditions from `SELECT MAX(id)+1`. Each id embeds the raw padded sequence value in a UNIQUE column, so startup also **forward-only resyncs** every sequence to its table max (`setval(GREATEST(last_value, max), true)` when max>0) — a checkpoint rollback/restore can reset a sequence below its table's max, after which `nextval` mints a duplicate id → 23505/HTTP 409 on the first insert.
- **RBAC role enum**: `director | supervisor | operator | viewer` stored in `users.roleEnum`; `requireRole(...roles)` enforces per-route role checks. `requireWriteRole(...roles)` (mounted at sub-router level) lets reads (GET/HEAD) pass for any authed user while gating writes (POST/PUT/PATCH/DELETE) to listed roles — makes viewer read-only everywhere. Director is included in every write list.
- **Security Standard SS-01** (permanent): every new endpoint must declare auth required? / minimum role / audit required? / rate limited? / input validation? / output sanitised? — before merge. `docs/security-matrix.md` is the authoritative per-endpoint reference.
- **Security Standard SS-02** (permanent): authorization is enforced by an automated regression test, not manual review. `lib/authz-matrix.ts` (every protected endpoint × 5 principals: director/supervisor/operator/viewer/anonymous) is the single source of truth shared by the SS-02 suite (`cert/authz-suite.ts`) AND the security dashboard, so they cannot drift. Run `pnpm --filter @workspace/api-server run test:authz` (validation command `authz`); any unexpected authz result fails certification. The suite retries on 429 with backoff so rate-limiting never misclassifies an outcome.
- **Security Standard SS-03** (permanent): the audit trail is verified by an automated regression test — the complement to SS-02 (SS-02 = *who may act*; SS-03 = *the act was recorded*). `artifacts/api-server/src/lib/audit-matrix.ts` (11 critical operations across BOTH append-only stores: `security_events` + the cell-receiving `cell_lot_events` timeline, with per-store field mapping) is the single source of truth for the SS-03 suite (`cert/audit-suite.ts`). It performs each real operation, then asserts the correct event persisted with all required fields (event type, actor, timestamp, entity id, details), and proves immutability two ways — static (no app route `.update()`/`.delete()`s an audit table) + runtime (a captured record is byte-identical after the run). Run `pnpm --filter @workspace/api-server run test:audit` (validation command `audit`); any audit mismatch or immutability violation fails certification. `ratelimit.exceeded` is shape-verified by default (set `CERT_AUDIT_RATELIMIT=1` to burst the auth limiter; restart api-server afterward to clear it). Mutating work runs on a throwaway cert lot + temp user torn down on exit.
- **Security Standard SS-04** (permanent): production configuration integrity is verified by an automated regression test. `artifacts/api-server/src/lib/config-integrity.ts` (`gatherConfig()` snapshots the live config; `validateConfig()` runs 34 checks across 12 categories — JWT/session, cookie, CORS, CSP, trust-proxy, rate limits, env vars, RBAC matrix, feature flags, manufacturing stage sequence, charging + battery-grading thresholds, version consistency) is the single source of truth shared by the SS-04 suite (`cert/config-suite.ts`) AND the `/developer/configuration` dashboard, so they cannot drift. Run `pnpm --filter @workspace/api-server run test:config` (validation command `config`); **a FAIL = configuration drift = production defect** and exits non-zero, while a **WARN** is allowed only for a documented dev-mode exception. The CSP rule fails on any production `script-src 'unsafe-inline'`; the admin-credential rule is value-aware (fails even if `ADMIN_PASSWORD` equals the known seed default). Read-only — performs no mutations.
- **CSP is environment-aware** (`lib/security-config.ts` `CSP_DIRECTIVES`, gated on `CSP_IS_PRODUCTION = NODE_ENV==="production"`): `script-src` drops `'unsafe-inline'` in production (kept in dev only for the Vite HMR client); `style-src` keeps `'unsafe-inline'` as a documented temporary exception (Radix/shadcn/Recharts inject inline `style=` at runtime), pending a nonce/hash migration. **Caveat:** the ocs-one frontend is served as STATIC files in production (`serve="static"` in artifact.toml), separate from the API server — so the helmet CSP governs API JSON responses (defense-in-depth), NOT the rendered HTML document. A static-serving/edge document CSP is a CW-02 recommendation.
- **Engineering Correction Framework (ECF)** (platform framework, CTO-approved pre-MAT-03) — the single audited correction process for OCS One. Any module that holds a *certified engineering record* corrects it through the ECF instead of re-implementing append-only/immutability/authorization logic. **One generic ledger `engineering_corrections` is the immutable history across all modules; the module table stays the source of truth for current state.** The lib (`@workspace/ecf`, `EngineeringCorrectionService`: `recordOriginal`/`correct`/`getHistory`/`validateCorrection`) is deliberately module-agnostic — it knows only `entityType`/`entityId`/`previousValue`/`newValue`(JSONB)/`reason`/`performedBy`/`approvedBy`/`auditEventType`/`metadata`(JSONB); `sequence` = engineering VERSION (1=original). Framework owns storage, version generation, unique Correction ID generation, reason+actor validation, role authorization (`actorRole ∈ allowedRoles`), and immutability; the module owns the entity row lock, business rules, value recalculation, snapshot update, and its own audit destination. Every row (originals included) carries a globally-unique **Correction ID `CORR-YYYYMMDD-NNNNNN`** from a global Postgres sequence (`ecf_correction_seq`, created at startup). `entityType` enum = 14 values (8 base CELL/BATTERY/PACK/SHIPMENT/QC_RECORD/CHARGING_SESSION/TEST_RESULT/WARRANTY_CASE + INVERTER/SOLAR_SYSTEM/EV_CHARGER/RAW_MATERIAL/BMS/CABINET). All writes run in a caller-provided transaction so the ledger write commits atomically with the module's state change + audit event. The ledger is in the SS-03 audit-immutability suite (static + runtime byte-identical). **Reusable ODS `OdsCorrectionHistory`** renders a module-agnostic genealogy (version, Correction ID, actor, reason, previous→new field diff). **Only Cell Grading is migrated** (the reference consumer); no other module, by direction. **Why:** generalize the proven Cell-Grading correction engine once so every module benefits (platform-improvement, not module-specific). **FROZEN at v1.0 (CTO directive):** the 4 interfaces (`recordOriginal`/`correct`/`getHistory`/`validateCorrection`) are stable contracts; the generic ledger is the *only* correction history (no module builds its own); every correction-allowing module MUST integrate with ECF (future work, NOT during CW-02); Engineering Version (`sequence`) and Correction ID `CORR-YYYYMMDD-NNNNNN` are official platform references that never reset/renumber. No ECF expansion during CW-02 — improvements are enhancement requests for after all cert waves; keep the framework extensible (attachment metadata must land without changing the correction API). **Compatibility Rule:** once a module uses ECF its integration contract stays backward compatible — existing APIs keep working, correction records stay readable, Correction IDs never change, Engineering Versions stay valid, new capabilities are additive; any breaking change is **ECF v2.0** only (explicit migration plan + compatibility review). **Enhancement backlog** (ID/desc/value/modules/complexity/target version) tracks ECF-001 Attachments, ECF-002 Digital Approval Signatures, ECF-003 Multi-level Approval Workflow, ECF-004 NCR/CAPA Integration, ECF-005 External ERP/MES Sync — none built during cert waves unless a cert defect requires a platform fix. Full guide: `docs/engineering-correction-framework.md`.
- **Controlled measurement correction (append-only)** — graded cells are corrected, never silently overwritten. **(Now implemented on top of the ECF — see above; this describes the Cell-Grading behavior the ECF preserves.)** `cell_grade_measurements` is an append-only versioned store (one row per measurement event: `sequence`, `measurementType` `original|correction`, the measurement values, computed grade/status, `gradedBy`, `correctionReason`, `createdAt`). The first grade writes `sequence=1` `original`; `POST /cells/{id}/correct` (supervisor/director only, **mandatory `correctionReason`**) recomputes the grade, appends a new `correction` row (`sequence=max+1`), updates the `cells` snapshot to reflect the active (latest-sequence) result, and emits a `cell_grade_corrected` audit event on the `cell_lot_events` timeline. Originals are immutable; the full genealogy is reconstructable via `GET /cells/{id}/measurements`. **Why:** factory traceability requires that a mis-entered measurement be re-graded by an authorized actor with a recorded reason, while the original record is preserved for audit. **Observations (future scope, not yet built):** (1) generalize this append-only + mandatory-reason + immutable-original pattern into a reusable platform framework for other editable certified records (test results, stage data); (2) repo-wide SS-01 sweep for other unconstrained numeric engineering-value schemas (the DEF-CW02-004 pattern — bare `number` with no `minimum`).
- **Persistent security audit** — `security_events` table records auth (`auth.login.success`/`failed`, `auth.logout`), `user.created`, `authz.denied` (403s), and `ratelimit.exceeded` events via fire-and-forget `recordSecurityEvent()` (`lib/security-events.ts`). `lib/security-config.ts` is the single source for CSP / rate-limit / cookie / JWT config (`describeJwtConfig`/`describeCspStatus`).
- **No public registration** — `/auth/register` is director-only (`requireAuth` + `requireRole("director")`), rate-limited, audit-logged (`event: user.created`), and issues no session cookie for the created user. Factory software: users never self-register.
- **Orval split mode** — codegen generates one file per tag rather than one giant file; barrel re-exports from `lib/api-client-react/src/index.ts` and `lib/api-zod/src/index.ts`.
- **Trust proxy = 1** — Replit's reverse proxy sets `X-Forwarded-For`; without this express-rate-limit throws `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR`. Must always be set before rate limiter middleware.
- **ESLint flat config** — `eslint.config.mjs` uses `typescript-eslint` recommended rules; `no-explicit-any` is off (ORM/generic callbacks make it impractical), `no-unused-vars` is error with `^_` ignore pattern; `.local/**` excluded.
- **Unified Product Platform (architecture FROZEN v1.0 — approved 2026-06-28, NOT yet implemented).** Everything leaving the factory becomes a serialized **Product** created at the QC-pass gate; every downstream module (Packing, Dispatch, Dealer, Inventory, Reports, Director) references the Product. **Four orthogonal concepts**, each its own master: **A Product Category** (`product_categories` — Battery Pack / Inbuilt Lithium Inverter / Hybrid Inverter), **B Product Model/SKU** (existing `master_products` — stays the model master, never serialized), **C Manufacturing Workflow** (`product_workflows` — BATTERY/INBUILT_LITHIUM/HYBRID, independent of Category), **D Product** (`products` — serialized unit). Plus a supporting **Manufacturer master** (`master_manufacturers`); Product *derives* manufacturer via `model_id → manufacturer_id` (never duplicated). **Unified serial:** one `official_product_serial` (unique) + `serial_source` enum (OCS|MANUFACTURER); downstream uses only the official serial, never the source; component serials live in genealogy. **Permanent rule: No Product before QC PASS.** Migration is strictly additive (no certified table renamed/removed; `production_order_id` dual-keyed; legacy refs retired only post-cert). Consumes frozen platforms (ODS/ECF/Security/Cert) unmodified. **FROZEN v1.0:** no new architectural concepts during CW-02→CW-08 except to fix a Critical cert defect; implementation begins after CW-02 closes per the phased plan; future ideas go to the Product Platform Enhancement Backlog (PP-001..PP-006). Full review + diagrams + freeze + backlog: `docs/architecture/unified-product-platform-review.md`.

## Product

- **Cell receiving & grading** — inbound cell lot creation, individual cell grading (capacity, IR, voltage), grade configuration, and controlled supervisor+ grade correction (append-only history, mandatory reason, immutable original)
- **Cell matching** — automated slot allocation for battery packs, reserve/release cells
- **Manufacturing orders** — full stage lifecycle (cell allocation → assembly → compression → BMS install → BMS programming → charging → testing → QC → packing)
- **Stage cards** — per-stage UI for operators: start/pause/resume/complete/approve/reject with data capture
- **Director dashboard** — real-time KPI metrics across all stages, pipeline health monitor, alert feed
- **Security dashboard** (`/developer/security`, director-only) — 12 sections: users-by-role, live authorization matrix, failed logins, rate-limit events, account creations, permission failures, audit feed, event histogram, SAST/privacy scan summary, dependency audit, CSP status, JWT/session + certification status
- **Configuration dashboard** (`/developer/configuration`, director-only) — live configuration-integrity report from the same `gatherConfig()`/`validateConfig()` SS-04 uses; every check grouped by category with pass/warn/fail + expected-vs-actual (never exposes secret values)
- **Logistics** — dispatch orders, dealer management, shipment events
- **Masters** — products, BMS, cells, chargers, test equipment, connectors, cables, busbars, cabinets

## User preferences

- **Cert-wave triage — module-specific vs. platform improvement (ask FIRST, every wave).** At the start of every certification wave, before fixing any defect, classify it: _"Is this defect module-specific, or is it a platform improvement?"_
  - **Module-specific** → fix only that module.
  - **Platform improvement** → fix it once in the shared framework (ODS, hooks, middleware, API/security layer) so **every** module benefits, not just the one under cert.
  - Precedent (fixed once, now benefit every module): ODS keyboard navigation, RBAC, performance dashboard, authentication, error handling. Default to the platform-level fix whenever a defect is systemic.
- **Batch MAT cycle — run the WHOLE phase before fixing anything (every cert wave).** For each MAT phase: (1) run the ENTIRE phase's tests as a batch — every case, no stopping; (2) collect ALL defects; (3) classify each Critical / High / Medium / Low; (4) present the full defect set to the CTO and get approval BEFORE any fix; (5) fix all Critical/High/Medium together in one remediation pass; (6) re-run the FULL phase; (7) close the gate; (8) only then proceed. NO per-defect test→fix→retest loops. Mantra: _Do not assume. Measure. Verify. Document._
- **Platform Freeze Policy — frozen platforms are consumed assets, not dev areas (CW-02 → CW-08).** The platform frameworks — **ODS**, **ECF**, **Security Standards** (SS-01..SS-04), and the **Certification Framework** — are FROZEN. Do NOT expand any of them during CW-02 through CW-08. A frozen framework may be modified ONLY when: (a) a **Critical** certification defect is found, (b) a **High-severity** certification defect is found, or (c) a **security vulnerability** requires immediate remediation. Every other idea (improvement, nice-to-have, refactor) goes into the relevant framework's **enhancement backlog** (e.g. the ECF backlog) and waits for the post-certification roadmap. Engineering focus shifts from *building frameworks* to *building manufacturing capability* on top of the frozen baseline. When tempted to touch a framework, first ask: _does this meet the Critical / High / security-vuln gate?_ If not, backlog it.
- **Platform Scorecard = operational dashboard; check it FIRST before touching any platform.** `docs/platform-scorecard.md` is an operational dashboard (not a governance doc) — **the first place to look before deciding whether a platform framework needs modification.** Platforms are measured by both **Adoption** (capability built on top) and **Platform Health** (stays stable while adoption grows); a healthy platform supports *more* manufacturing capability with *fewer* changes over time. Each frozen platform (ODS, ECF, Security Standards, Certification Framework) maintains ten fields: Version · Freeze Status · Modules Using It · Last Platform Change · Open Critical Defects · Open High Defects · Breaking Changes Since Freeze · Certification Status · Next Planned Version · Enhancement Backlog Count. Headline adoption metric = **Modules Using It** (grow while Version stays put); headline health metrics = **Open Critical/High Defects = 0** and **Breaking Changes Since Freeze = 0**. A frozen platform is touched only when those defect counts go non-zero or a security vuln demands it. Update the scorecard when a module adopts a platform, a permitted change ships, a defect opens/closes, or at each cert-wave gate.

## Gotchas

- **Always run `pnpm --filter @workspace/db run push` after schema changes** before starting the server — otherwise routes using new columns will error.
- **After codegen, check `lib/api-zod/src/index.ts`** — Orval may regenerate it and duplicate exports; the barrel must use `export * as types from "./generated/types"` (not `export *`) to avoid re-export conflicts.
- **Admin seed**: `admin@ocs.local` / `OCS@Admin2026!` (director role) — created on first startup if missing.
- **`app.set("trust proxy", 1)`** must come before any `express-rate-limit` middleware or Replit's `X-Forwarded-For` header causes validation errors.
- **Postgres sequences** (`mfg_order_seq`, `mfg_battery_seq`, `ecf_correction_seq`) are created by `seed.ts` at startup (`CREATE SEQUENCE IF NOT EXISTS`) and then **forward-only resynced** to their table max. If an id-minting path 409s on a fresh entity, compare the sequence's `last_value` to `MAX(split_part(col,'-',3)::bigint)` — a desync from a rollback/restore is the usual cause.
- **Vite pre-transform errors** after codegen are stale HMR cache — restart the ocs-one workflow to clear.
- **`CirclePlay`** (not `PlayCircle`) is the correct lucide-react icon name in v0.511+.
- **All-optional Zod update bodies need an empty-body guard** — `UpdateCellGradeConfigBody` has all-optional fields, so `{}` passes `.parse()` but then `db.update().set({})` throws on an empty SQL SET clause → 500. Reject empty bodies with 400 (`Object.keys(body).length === 0`) per SS-01. Applies to any all-optional PATCH/PUT schema.
