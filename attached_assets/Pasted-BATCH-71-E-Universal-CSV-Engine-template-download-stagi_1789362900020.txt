── FROZEN CSV CONTRACT (generator and parser are one pair; A16/A8/round-4 §6):

• Generated by GET /api/inventory/imports/template?material_id=… (&

template_version_id optional) FROM THE 71-C PREVIEW PAYLOAD — one

definition, all consumers.

• Metadata header lines (commented #):

#template:   #version:   #generated:   #hash:

• Column header row — SYSTEM COLUMNS (identity/quantity, A16) then

ATTRIBUTE COLUMNS then optional unit columns:

supplier_code, material_code, lot_number, quantity,

<attribute_code>…, <attribute_code>unit… (unit cols only for unit-

bearing attributes; optional)

• Importer maps columns BY HEADER NAME (attribute_code), never position;

unknown column → session-level error INVALID_SCHEMA; stale template

(#version ≠ pinned/resolved) → 409 STALE_TEMPLATE (D-attr-16).

• Channel parse per row: numeric attr cell → {value}; unit col → supplied_unit;

everything else → {raw} string. Produces CanonicalCaptureInput rows

(source.type CSV, source.session_id, source.row_ref=rowNumber).

── ROUTES (imports.ts; router.use(requireAuth); mutations supervisor+director)

GET  /template?material_id=&template_version_id= → text/csv attachment

(filename <template_code>v.csv). Resolution + version pinning via

the 71-C resolver; NO_TEMPLATE → 422.

POST /  body { csv: string, filename?: string } → 201 session

• sha256(csv) = file_hash. Import-level idempotency (A10): existing

session with same file_hash (+ same pinned template) → 200 returns

the EXISTING session, no new staging.

• Resolve+pin template version from the csv's #template/#version

metadata (A11); mismatch vs resolved → 409 STALE_TEMPLATE.

• Parse rows → stage import_rows (PENDING) → run the shared 71-B

validator per row → row status VALID/INVALID with A14 errors

(row/attribute_code/rule/input/normalized/message).

• Session counters (total/valid/invalid); status VALIDATED.

• Outbox IMPORT_SESSION_CREATED in-tx.

GET  /:id → session + rows (with errors) — this IS the dry-run preview (A9;

nothing reaches the GRN service from a read).

POST /:id/confirm  header Idempotency-Key (business idempotency A10):

• Replay: confirmKey seen → 200 returns existing downstream GRN.

• STRICT (A9): any INVALID row → 409 SESSION_HAS_INVALID_ROWS,

ZERO GRN created. Any PENDING → 409 ROWS_NOT_VALIDATED.

• Else: adapter.confirmBatch(validRows) → ONE GRN draft with one line

per row (all rows must share supplier? NO — group by supplier_code;

MULTIPLE suppliers ⇒ one GRN per supplier group; document in

evidence). Captures persisted per line by the adapter (source_type

CSV, source_session_id, source_row_ref). Session → CONFIRMED,

downstream_document_id set (single supplier case) or jsonb map for

multi-supplier (keep single-supplier enforced in Phase 6 for

simplicity? DECISION: enforce single supplier per import in Phase 6

— mixed suppliers → 422 MULTIPLE_SUPPLIERS; multi-supplier imports

are a later feature. Flagged for owner ratification below.)

• Outbox IMPORT_CONFIRMED in-tx with file_hash, counts, GRN id.

POST /:id/cancel → DRAFT/VALIDATED → CANCELLED (no downstream effect).

numbering, same internal flow as 71-D) with one line per input, persisting
