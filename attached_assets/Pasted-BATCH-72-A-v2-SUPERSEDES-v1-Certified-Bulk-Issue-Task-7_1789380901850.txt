PART 3 — THE ENDPOINT (POST /api/manufacturing/orders/:id/issues/bulk)

Header Idempotency-Key REQUIRED. Body { notes?: string }.

ONE db.transaction. Deterministic lock order (owner-mandated):

1. production order FOR UPDATE

2. BOM snapshot header + lines (unique per PO)

3. SORTED material identities — process order = material code ASC

(duplicate BOM material lines AGGREGATED here: sum quantities, collect

sourceBomLineRefs) → one reservation + one issue note per material

4. reservations / lots / GRN lines — acquired inside the extracted

helpers in the same deterministic order (allocator already scans

lots in FIFO order with line locks)

Flow:

a. Lock PO. Load snapshot; AGGREGATE lines by material (code ASC).

b. requestHash = sha256(order_id + aggregated lines).

c. Advisory lock 'bulk-issue:'+key. SELECT bulk_batches by key:

found + requestHash match   → 200 replay of stored projection

found + requestHash differs → 409 IDEMPOTENCY_CONFLICT

d. MUTUAL EXCLUSION: active MIN exists for this order (existing MIN

active-status definition) → 409 ACTIVE_MIN_EXISTS (zero effects).

Reverse guard in MIN create (72-A scope, additive): active bulk batch

exists → 409 BULK_BATCH_EXISTS. Both directions prevent mixed state.

e. Insert bulk_batches (status COMPLETED placeholder within tx).

f. Per aggregated line: createReservationInTx → allocateInTx →

issueToWipInTx; insert bulk_batch_lines (sequence, links, quantities).

g. Outbox BULK_ISSUE_CREATED (aggregate payload) in-tx; security event.

h. Any failure ⇒ whole tx rolls back (atomicity).

Response 201: the batch projection (stored shape: batch id, PO, lines with

reservation/note/lot details) — same shape returned on replay.
