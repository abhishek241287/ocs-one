// ADD this validation function in the lib file (or inline in the route):

async function validateLotAllocation(
  materialId: string,
  grnLineId: string,
  lotNumber: string,
  requestedQty: number,
  tx: any
): Promise<{ valid: boolean; error?: string }> {
  // 1. Verify GRN line exists and matches material
  const grnLine = await tx.query.grnLineItems.findFirst({
    where: eq(grnLineItems.id, grnLineId),
  });
  if (!grnLine) {
    return { valid: false, error: `GRN line ${grnLineId} not found` };
  }
  if (grnLine.materialId !== materialId) {
    return { valid: false, error: "GRN line does not match requested material" };
  }

  // 2. Verify lot number matches the GRN line
  if (grnLine.supplierLotNumber !== lotNumber) {
    return { valid: false, error: `Lot ${lotNumber} does not match GRN line (expected ${grnLine.supplierLotNumber})` };
  }

  // 3. Acquire transaction-level advisory lock on (materialId, lotNumber)
  const lockKey = `lot:${materialId}:${lotNumber}`;
  await tx.execute(sql`SELECT pg_advisory_xact_lock(hashtext(${lockKey}))`);
  // Note: pg_advisory_xact_lock is auto-released on commit/rollback

  // 4. Calculate available balance from signed ledger
  //    Join inventory_transactions → grn_line_items via source_line_id
  //    Filter stock_state = 'available' (required — inspection_pending and rejected are NOT issuable)
  const [balanceRow] = await tx
    .select({ total: sum(inventoryTransactions.quantity) })
    .from(inventoryTransactions)
    .innerJoin(grnLineItems, eq(inventoryTransactions.sourceLineId, grnLineItems.id))
    .where(and(
      eq(inventoryTransactions.materialId, materialId),
      eq(grnLineItems.supplierLotNumber, lotNumber),
      eq(inventoryTransactions.stockState, "available")  // REQUIRED: only available stock is issuable
    ));

  const available = Number(balanceRow?.total ?? 0);
  if (available < requestedQty) {
    return {
      valid: false,
      error: `Insufficient lot balance: available ${available}, requested ${requestedQty}`
    };
  }

  return { valid: true };
}

# O. FINAL DEFINITION OF DONE

## O.1 For "Full Inventory Management"

The OCS One system satisfies FULL INVENTORY MANAGEMENT when ALL of the following are true:

1. **Procurement:** Purchase orders can be created, approved, and tracked. GRNs can be received against POs with over-receipt control.
2. **Receiving:** GRNs support partial receipt. Inspection supports partial and re-inspection. Internal lots are created. Corrections and reversals are supported.
3. **Master Data:** Warehouse, location, and bin masters exist. General lot/batch tracking exists. UOM is a controlled master.
4. **States:** All 11+ inventory states are defined and tracked: on-hand, available, reserved, allocated, issued, WIP, consumed, returned, quarantined, scrapped, adjusted.
5. **Reservation:** Stock can be reserved, released, and cancelled. Reservations are order-linked and expiry-controlled. Competing reservations are protected.
6. **Allocation:** Material, lot, and location allocation are supported. FIFO/FEFO policies are enforced.
7. **Transfers:** Multi-step transfers (request/issue/receipt) are supported. Cancellations and reversals are supported.
8. **Manufacturing Flow:** Complete lifecycle: Reserve → Issue → WIP → Consume → Return → Scrap. Each step is distinct and tracked.
9. **BOM:** BOMs have effective dates. Production orders snapshot the BOM at creation. Scrap/yield factors are supported.
10. **Material Issue:** Full and partial issues are supported. Lot and location selection are validated. Reservations are consumed. Shortages are handled. Reversals are supported.
11. **Consumption:** Actual consumption is confirmed separately from issue. Variance (over/under) is calculated and reported.
12. **Returns:** Production returns, WIP returns, and unused material returns are supported. Lot and location are tracked.
13. **Scrap:** Scrap documents with reason, quantity, lot, and production linkage are supported. Approval and ledger movement are enforced.
14. **Adjustments:** Positive and negative adjustments with reason, approval, lot/location scope, and audit trail are supported.
15. **Stock Ledger:** The ledger covers all transaction types with sign convention, source document, lot, location, production order, user, timestamp, and reversal relationship.
16. **Stock Balances:** Multi-dimensional balances are queryable: material × lot × warehouse × location × state.
17. **Traceability:** Complete genealogy from supplier → PO → GRN → lot → issue → WIP → consumption → production → finished product. Return and scrap branches are included.
18. **Cell Processing:** Cell subsystem remains integrated and functional.
19. **Reconciliation:** Automated reconciliation of ledger, on-hand, lot balances, location balances, reservations, WIP, and production consumption.
20. **Reporting:** All required reports are available: current stock, available stock, reserved stock, lot stock, location stock, movements, GRN, PO, issues, consumption, returns, scrap, adjustments, transfers, WIP, production variance, inventory valuation, and complete traceability.
21. **Authorization:** Every inventory operation has role-based authorization.
22. **Audit:** Every inventory operation generates a durable audit event.
23. **Concurrency:** All inventory operations are protected against race conditions under concurrent load.
24. **Tests:** All FAT scenarios (INV-FAT-01 through INV-FAT-20) pass.
25. **Evidence:** All capabilities are evidenced by test results, audit trails, and documented acceptance criteria.
