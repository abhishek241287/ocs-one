§1. WHAT GENEALOGY MUST ANSWER (the question set — freeze this first)

═══════════════════════════════════════════════════════════════════════════

UPSTREAM (where did this come from):  Given a production order / finished

serial / dispatch unit → which materials, lots, supplier lots, GRNs,

receipts (with Phase 6 captured attributes) fed it? Per component and

in total. Reverse recall: given a supplier lot (or a recalled attribute

range, e.g., capacity < 270 Ah) → which orders/serials/units consumed it?

DOWNSTREAM (where did this go):  Given a receipt lot / cell lot → which

reservations/allocations/issues/consumptions, orders, and (via output

links) which finished serials/dispatches?

COMPOSITION (what is it made of):  Given a finished serial → full BOM

explosion with actual lot/serial instances (not just BOM snapshot lines).

PROVENANCE INTEGRITY:  every genealogy edge cites its certified source

document (no inferred edges — the MIN lesson: never derive movement from

documents that don't carry lot links).

§2. WHAT ALREADY EXISTS (certified links — REUSE, all invariant-gated)

═══════════════════════════════════════════════════════════════════════════

RECEIPT→LOT      GRN line → inventory_lots (grnLineId), supplier lot number

on the line; Phase 6 captures on GRN lines (attributes,

serial-scope values deferred).

LOT→RESERVATION→ALLOCATION→ISSUE  certified 69 chain: allocations bind lot

+ GRN line quantities to a reservation for a PO.

ISSUE→WIP→CONSUMPTION  certified 70 chain: wip_issue_lines bind allocation

rows; wip rows (PO+material+lot+note); consumption_confirmations

(PO+material+lot, planned vs actual, variance).

RETURN/SCRAP     wip rows accumulate returned/scrapped per lot.

TRANSFERS        transfer_requests/lines + Option A — lot-keyed movements.

ORDERS           mfg_production_orders (+stages, bom snapshot unique per PO,

cellMatchId/chargerUnitId link fields — VERIFY).

FRONTEND         TraceabilityPage exists (text-field serial/PO lookup —

survey §2) — a natural host for genealogy views.

VERIFICATION STORAGE  Phase 6 attribute_capture_values: typed, queryable,

lot/material/serial scope-aware — the attribute-side of

genealogy (recall by capacity/IR/etc. becomes a query).

§3. WHAT'S MISSING (the gaps)

═══════════════════════════════════════════════════════════════════════════

GAP-1  OUTPUT GENEALOGY: certified chains stop at the PO. The link

PO → produced output (finished-good serial / product unit /

dispatch) is the missing downstream edge. VERIFY what exists:

products module serials? packing/dispatch serials? mfg order

completion creating product inventory? (schema index shows

products, dispatch, packing, logistics modules — inspect.)

GAP-2  COMPOSITION LINKS: parent-child assembly edges (cell lots → pack

lot; pack → module) beyond single-material consumption — VERIFY

whether any 'output lot' concept exists today (likely not certified;

candidate: new output_lots/production_outputs table, or extend wip

consumption with an output link).

GAP-3  SERIAL INDEX: serial-number → entity resolution (the 71-F deferred

item). Serial-tracked materials exist (profiles SERIAL/LOT_AND_SERIAL)

but no serial index table → scan resolves UNKNOWN; genealogy by

serial needs it.

GAP-4  GENEALOGY QUERY API + REPORTS: traversal endpoints (upstream/

downstream/composition/recall-by-attribute) + the TraceabilityPage

wiring. Read-only, document-cited edges only.

GAP-5  RECALL ENGINE: attribute-range recall (capacity < X, chemistry =

LFP + date range) across captures → affected orders/serials. Built

on Phase 6 typed values (index-backed), not on string parsing.

§4. PROPOSED DECISIONS (ratify before 73-A)

═══════════════════════════════════════════════════════════════════════════

D-gen-1  EDGE PRINCIPLE: genealogy edges are READS over certified document

links only. NO new movement semantics; NO inferred edges; every

edge in a response cites its source document id/type. (The MIN

lesson, constitution-grade.)

D-gen-2  OUTPUT MODEL (pending §3 GAP-1 verification — two candidates):

(a) if the products/dispatch side already has production-output

records, link genealogy to them additively; (b) if not, introduce

production_outputs (id, production_order_id, output entity type/

id, lot/serial, quantity, uom, created via certified order-

completion step) — completion becomes the single writer.

D-gen-3  SERIAL INDEX: serial_units (serial_number unique, material_id,

lot_id nullable, capture_instance_id nullable, status) written by

the certified paths that already see serials (receipt captures

with SERIAL scope, scan hybrid, future outputs). 71-F QR decode

upgrades from UNKNOWN to resolved via this index.

D-gen-4  RECALL = query over attribute_capture_values typed columns +

template version scoping; result = affected GRN lines/lots →

traverse certified edges to orders/outputs. Read-only.

D-gen-5  INVARIANTS (new family, additive): INV-GEN-01 every genealogy

edge resolves to an existing certified source document;

INV-GEN-02 serial index entries reference existing lots/captures;

INV-GEN-03 output records reference completed orders and existing

lots; INV-GEN-04 recall results are reproducible (deterministic

query, no time dependence beyond frozen parameters).

D-gen-6  FRONTEND: TraceabilityPage becomes the genealogy console

(upstream/downstream/composition/recall tabs); no new write paths.
