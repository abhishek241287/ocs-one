STEP 2C — PROPOSED LIFECYCLE (state transitions)

═══════════════════════════════════════════════════════════════════════════

inventory_reservations:      active → partially_allocated → fully_allocated

↓ issue (partial or full)

partially_issued → fully_issued

↓ consumption (of the issued qty)

(terminal for Task scope; release-after-partial-issue

releases only the still-allocated remainder)

inventory_reservation_allocations: active → issued  (per issued lot quantity)

inventory_transactions (stock_state): available −qty │ +qty wip   ← ISSUE (physical move)

wip        −qty            ← CONSUMPTION (physical use)

wip_inventory:  upsert per (PO, material, lot, issue-doc): issuedQty ↑, then

consumedQty ↑; remainingQty via CHECK; status active →

partially_consumed → fully_consumed.

consumption_confirmations: draft → confirmed (planned vs actual → varianceQty),

or → rejected; 'adjusted' reserved for post-hoc correction.

THE ONLY OPERATIONS THAT CHANGE PHYSICAL INVENTORY: ISSUE (available→wip) and

CONSUMPTION (wip destroyed into the product). Reservation/allocation alone

never do (certified Task #69 rule, unchanged).

STEP 2D — ACCOUNTING MODEL

═══════════════════════════════════════════════════════════════════════════

ISSUE (from a reservation, lot-forced by allocation):

• ledger: −qty stock_state='available', +qty stock_state='wip' — BOTH keyed to

the lot's GRN line dims (lotId/warehouseId/locationId/binId) + productionOrderId

+ source_document (issue doc). No net material change; state migration only.

• reservation: allocatedQty −= qty; issuedQty += qty; status → partially_issued/

fully_issued (existing CHECK reserved ≥ allocated ≥ issued enforced by DB).

• allocations: consumed rows flip active → 'issued' (partial issue splits the row).

• wip_inventory: upsert (PO, material, lot, issue-doc) issuedQty += qty.

CONSUMPTION (confirm actual use):

• ledger: −qty stock_state='wip' (wip decreases; consumed stock leaves inventory —

the product is tracked by the mfg order, not material stock).

• wip_inventory: consumedQty += qty (CHECK keeps remaining consistent).

• consumption_confirmations: actualQty recorded vs bom snapshot plannedQty;

varianceQty = actual − planned (DB CHECK).

TRANSFERS: not involved in issue/consumption (Option A untouched). Transfers move

available→cell-processing; issue moves available→wip. Both lock GRN lines.

LOTS: preserved end-to-end — every ledger row and wip row carries lotId; lot.status

never mutated by issue/consumption (a lot is 'consumed' only via lots lifecycle).

RESERVATIONS: issue consumes allocations (allocated→issued); release-after-partial-

issue releases only the non-issued remainder; cancel-after-issue rejected once

issuedQty > 0 (or cancels remainder only — decision flagged below).

CONSISTENCY: available(material) = Σ ledger 'available'; reserved = Σ holding

reservations; wip(material) = Σ ledger 'wip'; invariant: available + wip +

consumed-never-negative, and issued(reservation) ≤ allocated ≤ reserved always.

STEP 2E — CONCURRENCY MODEL (reuse existing locks; nothing new invented)

═══════════════════════════════════════════════════════════════════════════

ISSUE:  1) inventory_reservations row FOR UPDATE (serializes vs release/cancel/

concurrent issues on the same reservation)

2) allocation rows of that reservation, GRN-line order (deterministic —

same order Task #69 allocate uses) → lot rows FOR UPDATE

3) each GRN line FOR UPDATE — THE SAME LOCK OBJECT transfers.ts takes,

so issue vs transfer is serialized (transfer locks one line only →

no deadlock cycle possible)

CONSUMPTION: wip_inventory row FOR UPDATE (unique PO+material+lot+issue) —

serializes concurrent consumption; issue upserts the same row under

the reservation lock, so issue-vs-consumption on one row is ordered.

RESERVATION INTERACTION: release/cancel also take the reservation row lock

FIRST → issue vs release/cancel fully ordered. Material-level create

advisory lock (Task #69) is unaffected (issue never changes reserved).

IDEMPOTENCY: state machine + row locks give at-most-once per transition;

a retried issue re-reads the locked reservation and 409s on

over-issue instead of double-writing.

STEP 3 — RISKS (identified, not yet solved)

═══════════════════════════════════════════════════════════════════════════

R1 Double issue of the same allocation          → allocation flip to 'issued' under row lock

R2 Issue > allocated/reserved                   → reserved ≥ allocated ≥ issued CHECK + app guard

R3 Issue > physically available                 → line ledger re-read under GRN-line lock

R4 Lot mismatch (issue from wrong lot)          → allocations bind lot; forced-lot validated

R5 Consumption > issued                         → wip CHECK + remaining validation under row lock

R6 Concurrent issue race                        → reservation row lock

R7 Concurrent consumption race                  → wip row lock

R8 Ledger duplication (double submit)           → state machine + locks; retries idempotent-by-state

R9 Negative stock                               → DB CHECKs (wip remaining) + invariant SQL

R10 Reservation inconsistent after issue        → allocated/issued moves are one tx with outbox

R11 Wrong lot/location attribution              → dims copied from allocation's lot, never client-free

R12 Transfer↔issue deadlock                     → analyzed: none possible (transfers lock 1 line)

R13 Retry/idempotency                           → at-most-once by state; optional idempotency_key later

R14 Audit/outbox tx consistency                 → outbox insert inside same tx (house pattern)

R15 MIN regression                              → MIN untouched; new flow lives beside it
