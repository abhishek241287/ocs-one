DATA / SCOPE BOUNDARY — HARD RULE

═══════════════════════════════════════════════════════════════════════════

UI-IA-01 is a frontend information-architecture and presentation batch.

It may use ONLY: existing frontend hooks · existing generated-client hooks ·

existing API responses · deterministic client-side presentation calculations

· existing localStorage patterns.

It MUST NOT introduce: new backend endpoints · new database queries · new

backend fields · API aggregation · polling infrastructure · new business-

state calculations · inferred production states · fabricated dashboard

metrics.

If a requested dashboard datum cannot be produced deterministically from the

audited existing frontend data sources: DO NOT GUESS. DO NOT PATCH THE

BACKEND. DO NOT INVENT A DERIVATION. Omit the datum and record it in the

UI-IA-02 stop-list.

UI-IA-01 establishes hierarchy and presentation. UI-IA-02 is the authorized

batch for resolving the production-order Product/Progress stop-list and

enriching the production pipeline.

MY WORK RULE (amended): a presentation shell over ONLY the feeds explicitly

verified in audit §2. NO new endpoint, aggregation backend, inference, or

polling. If a feed isn't available from an existing endpoint, OMIT it and

record it in the stop-list.

Mechanics: collapsible sections with persisted open-state; active-route

highlight; role gates copied VERBATIM from current item definitions; dealer

handling preserved. The Production duplication dies per the audit's mapping.

---------------------------------------------------------------------------

PART 2 — DASHBOARD (restructure /dashboard into the hierarchy; spacing + type

scale, not competing card colors)

L1 FACTORY STATUS (amended): render ONLY statuses derivable deterministically

from the audited mapped endpoints. Do NOT invent status classifications

— Waiting/Blocked/Transit especially. Where a requested status cannot be

supported: omit it or use the existing equivalent and record the gap.

L2 MANUFACTURING PIPELINE (amended): primarily a VISUAL stage/navigation

model — the hero element. Per-stage counts displayed ONLY where existing

dashboard/order responses provide them. NO new aggregation queries,

backend fields, or derived lifecycle semantics. If counts aren't

available, show the stage with existing supported information only.

Stage click-through to the existing workspace.

L3 TWO-COLUMN: ATTENTION REQUIRED (actionable) | FACTORY ALERTS

(informational) — populated only from audit-verified feeds; same

omit-and-record rule.

L4 PRODUCTION ORDERS: Order # | Stage | Priority | Age — Age ONLY if

created_at is confirmed present in the current response (audit §6);

computed purely client-side; NO Product/Progress columns (stop-list).

L5 MY WORK strip — same feed rule as Part 1.

WIDGET DISPOSITION (amended): every LIVE/DERIVED widget remains accessible

(demoted into the ONE muted collapsible "Details" strip). STATIC/MOCK/

UNKNOWN widgets are NOT promoted and given no new operational meaning;

retain only where necessary for route/function preservation and RECORD

their disposition in the stop-list.
