DESIGN (the shape that must not drift)

• Manual GRN create accepts OPTIONAL `attribute_values`, keyed by the 1-based

line_number of the request's lines array:

attribute_values: [{ line_number: 1, attributes: [CanonicalAttributeValue…] }]

• Inside the EXISTING create transaction, after lines are inserted:

for each entry: resolve template (material, resolutionDate=now, via the

71-C resolution path / resolveTemplate) →

NO_TEMPLATE + attributes supplied  ⇒ 422 NO_TEMPLATE (whole create

ROLLS BACK — atomic, no partial GRN, no partial capture)

template found                     ⇒ build TemplateField[] from the

pinned version's attribute lines + definitions + unit registry rows

⇒ validateCapture() ⇒

errors ⇒ 422 CAPTURE_VALIDATION with the A14 machine-readable

error list (whole create rolls back)

ok     ⇒ insert attribute_capture_instances (target_type

GRN_LINE, target_id = line.id, template_version_id = PINNED

version, material_id, status VALIDATED — downstream draft exists,

source_type MANUAL) + attribute_capture_values rows.

• GRN detail: each line gains `capture: { template_version_id, template_id,

template_code, version_no, fields: [{ attribute_code, name, data_type,

value_text/value_num/value_bool/value_date, unit, value_origin, display }]

} | null` — joined read, additive field, existing fields untouched.

• ADAPTER: grn-adapter.ts registers { targetType: "GRN_LINE", confirm }.

confirm(canonicalInput, validated) creates a GRN DRAFT through the SAME

internal creation flow the route uses (ADJUST: extract/reuse the existing

create helper if present; otherwise the adapter builds the same insert

sequence via a shared exported function — ONE creation path, no

divergence). It is NOT wired to any route in 71-D; 71-E/F call it.
