OCS ONE — PHASE 9 UI MODERNIZATION GUIDELINE
Operations Experience Architecture
Status: Working guideline · Frontend modernization only
1. PURPOSE
OCS ONE has now reached a major architectural milestone.
The underlying system already provides certified capabilities for:
Inventory control
Reservations and allocations
Receiving
Lot tracking
WIP
Consumption
Universal attributes/capture
Manufacturing
Quality
Transfers
Production
Serial resolution
Genealogy
Recall
Packing
Dispatch
The current UI does not adequately communicate the strength of that system.
The objective of Phase 9 is therefore not simply to make the UI prettier.
The objective is:
Make the interface communicate the operational model of OCS ONE.
The UI should feel like an industrial operations platform / manufacturing command center, not a collection of CRUD screens.
2. CORE UX PRINCIPLE
The system should answer three questions in this order:
1. What is happening?
Command Center
2. What do I need to do?
Workspaces / My Work
3. What exactly happened to this object?
Object pages + genealogy
The architecture should therefore conceptually become:
                    OCS ONE
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
 COMMAND CENTER    WORKSPACES     OBJECT PAGES
 "What's now?"     "Do work"      "Trace anything"
This is the guiding principle for all Phase 9 UI decisions.
3. DO NOT DESIGN A "PRETTIER SIDEBAR"
The existing sidebar exposes too many individual functions.
For example:
Cell Master
BMS Master
Connector Master
Cable Master
Busbar Master
Cabinet Master
Product Master
Supplier Master
...
This exposes the implementation structure rather than the user's mental model.
The solution is not to delete functionality.
The solution is to reorganize information architecture.

5. MASTER DATA MUST REFLECT THE NEW ARCHITECTURE
The Phase 6/7 architecture is configuration-driven.
Therefore the UI should stop implying that every material type is a completely separate system.
Instead of:
Cell Master
BMS Master
Cable Master
Connector Master
Busbar Master
Cabinet Master
the conceptual model should become:
MASTER DATA
    ↓
MATERIALS
    ↓
Material Type / Category
    │
    ├── Battery Cell
    ├── BMS
    ├── Cable
    ├── Connector
    ├── Busbar
    ├── Cabinet
    └── Other Components
The individual functionality remains available through the Material workspace.
The UI should communicate the configuration-driven architecture that already exists underneath.
6. DASHBOARD = FACTORY COMMAND CENTER
The dashboard should not attempt to give every piece of information equal visual importance.
The primary question is:
What is happening in my factory right now, and what needs intervention?
Therefore establish this hierarchy.
LEVEL 1 — Factory Status
At the top:
FACTORY STATUS

Production       Inventory       Quality       Dispatch

12 Active        44 Available   0 Pending     2 Ready
4 Waiting        16 Allocated   2 Passed      0 Transit
2 Blocked        4 Rejected     1 Failed      1 Delivered
These are high-level operational states.
7. LEVEL 2 — MANUFACTURING PIPELINE
The manufacturing pipeline should become the hero element.
Conceptually:
RECEIVING
    →
GRADING
    →
MATCHING
    →
ASSEMBLY
    →
CHARGING
    →
TESTING
    →
QC
    →
PACKING
    →
DISPATCH
Each stage should communicate:
Active
Waiting
Blocked
Done Today
Example:
CELL GRADING

Active       0
Waiting      0
Blocked      4
Done Today   0
Interaction
Clicking a stage should take the user to the appropriate existing workspace/queue.
The dashboard is therefore not just displaying data.
It becomes a navigation surface for factory operations.
8. LEVEL 3 — ATTENTION REQUIRED
Do not display every metric as an alert.
Only surface things requiring intervention.
Example:
ATTENTION REQUIRED

🔴 4 cell grading jobs blocked
🟡 2 QC approvals required
🟡 1 rework pending
This section should answer:
What needs somebody's attention?
9. FACTORY ALERTS
Keep environmental/system alerts separate from operator work.
Example:
FACTORY ALERTS

⚠ Low cell inventory
⚠ Charger under maintenance
This prevents alerts and work queues from becoming one noisy list.

Important implementation rule
Progress and Age must initially be calculated client-side from existing response fields.
Do not invent backend fields.
If the required information does not exist:
STOP

Report:
- exact missing field
- current endpoint
- proposed minimal read-only additive
Only then should a backend-lite micro-decision be considered.
11. MY WORK
Introduce a task-oriented concept where supported by the existing application.
Example:
MY WORK

⚠ 4 Cell Grading jobs blocked
→ Resolve

2 QC approvals
→ Review

1 charger maintenance issue
→ View

3 orders ready for assembly
→ Start
The purpose is to prevent operators from navigating through multiple modules just to discover what they need to do.
The sidebar answers:
Where can I go?
My Work answers:
What should I do?

OCS ONE's genealogy capability is one of the strongest differentiators of the platform.
Users should not have to think:
"I need to find the genealogy page."

14. DOCUMENT-CITED EDGES MUST BE VISIBLE
The certified genealogy architecture is based on document-cited edges.
The UI should make that principle visible.
Whenever genealogy displays an edge/node backed by the API:
LOT-S1
Consumed: 120 pcs

[ ISSUE_NOTE · #1842 ]
or:
GRN-00182

Source:
GRN · #182
Every applicable genealogy edge should expose its document_cited information.
This is not decoration.
It is part of the trust model of OCS ONE.

18. HARD GUARDRAILS
Every Phase 9 batch must obey:
NO DATABASE CHANGES
NO BUSINESS LOGIC CHANGES
NO CERTIFIED BACKEND FLOW CHANGES
NO PERMISSION CHANGES
NO ROUTE REMOVALS
NO URL CHANGES
NO INFERRED DATA
NO NEW WRITE PATHS
NO GENEALOGY SHORTCUTS
NO COMPONENT-SERIAL UI
NO COMMIT
If something cannot be implemented using existing APIs/data:
STOP → identify the exact missing capability → propose the smallest possible change separately.
Never silently change the backend to make the UI easier.
19. VERIFICATION FOR EVERY UI BATCH
Every batch should produce evidence for:
Route preservation
Existing routes remain functional.
Permission preservation
Existing role access remains unchanged.
Backend diff
Frontend work must not silently modify certified backend behavior.
Typecheck
Pass.
Production build
Pass.
Manual authenticated smoke
Pass against real development data where applicable.
Write protection
Confirm the UI introduces no unintended write paths.
Automation
Do not claim authenticated UI automation until follow-up #90 is implemented.
20. MOST IMPORTANT DESIGN RULE
Before implementing any component, ask:
Does this help the operator understand what is happening, what needs action, or what happened to this object?
If not, it probably does not belong in the primary UI.
